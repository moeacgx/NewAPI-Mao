# 工单群通知标记与 Telegram 模板编辑

## 目标与方案

管理员从工单管理入口成功人工回复后，由现有通知调度任务将此前用户消息对应的 Telegram 原通知编辑为 `✅ 已回复` 加换行及原正文。系统自动确认、用户发言和单独修改状态不触发标记；后续用户追问发送新的未标记通知。

独立保存每次投递的用户消息 ID、Bot、Chat、Telegram 消息 ID 和 HTML 原文，避免通知中心仅保留五条历史导致关联丢失。按消息 ID 顺序检查后续人工回复，覆盖排队通知晚于人工回复才发送的情况，不让编辑失败回滚已成功的工单回复。每个目标独立处理，复用系统任务跨实例租约、取消和有限批次，编辑失败退避重试。

## 契约与边界

- 工单事件新增内部 `user_message_id`，不改变模板变量白名单和公共工单接口。
- 新增 `ticket_notification_messages` 表，通过 GORM 注册普通与快速迁移；SQLite、MySQL、PostgreSQL 使用相同查询语义。
- 只保存消息关联和原文，不保存 Bot Token；编辑使用发送时的消息位置和原文，不用后续模板或目标配置重渲染。Bot 停用或删除后不再编辑。
- 升级前已发送消息未保存 Telegram 消息 ID，无法补标。通知关联从发送成功起最多保留三天，超期按有限批次清理。工单删除后不再编辑。
- 编辑由十秒周期的通知调度执行，非回复请求内同步调用；429、网络和服务器错误有限重试，永久错误留脱敏原因。重复编辑收到“消息未修改”视为成功。
- 编辑成功立即删除后台跟踪记录和原文，群内勾选保留。人工回复本身不依赖 Telegram 请求；编辑失败保留独立重试状态。
- Default 与 Classic 通知中心分别增加格式工具栏、emoji 与变量插入、工单预设和在线样例预览。两套回复入口共用后端。原回复权限、计费和路由契约不变。
- 新默认工单模板使用 emoji、加粗及正文引用，精确旧默认升级，自定义模板保持不变。每次发送保存原位置与原文，后续改模板/群号不改变待编辑通知。
- `POST /api/notification/preview` 需要 Root、64 KiB 请求上限，用服务端样例返回 HTML 及字符数，不读实际工单、不发消息。前端防抖、取消/隔离旧响应，白名单转换为 React 元素。
- 格式校验共用于预览、保存和发送，限制 Telegram 支持标签/属性与链接协议；变量只能放文本。为固定的已回复标记预留长度预算，普通模板文字和 emoji 可在后台自由编辑。
- 普通和快速迁移新增关联表，保留最多三天（成功立即删除）。升级前已发送消息因无 Telegram ID 不补标；Telegram 与数据库不能原子提交，回执落库失败保留失败/未知记录且不自动重发，可能无法自动打标。
- 不调用真实 Telegram 或生产接口，不执行发布、部署或线上迁移。回滚保留新增表即可，旧程序忽略关联，不再自动标记。

## 补充：三天保留与规则清理

用户要求不用规则后不残留消息 ID/正文，优先自动清理。将原来的 90 天缩短为三天，并在规则停用和物理删除事务中清除所属关联，不新增前端清理按钮或生产数据操作。

关联增加独立 `task_id` 索引，不能依赖仅保留五条的投递历史；新增非空整数列使用 `default:0` 兼容 SQLite 非空表迁移。已有无归属关联继续按发送时间三天到期清理。完成发送回执时在序列锁内重读规则及启用基线，旧发送不因“停用后重新启用”而重建关联；已成功的外部发送仍记录成功，不重发。

测试计划覆盖三天阈值、不同状态与未来重试时间、无回复唤醒清理、历史裁剪后按规则清理及其他规则隔离、事务回滚、发送中停用/重新启用，以及成功编辑立即释放。清理仅作用于后台原通知跟踪，工单、群消息和通用事件去重凭据保留原生命周期。共享 API 与 Default/Classic 页面保持原契约。

补充验收：先运行新增回归确认旧行为失败，再实现三天期限和规则清理，定向测试通过。最终 `go test -mod=readonly ./controller ./service ./model ./router -timeout 60s -count=1` 四包全部通过；`go vet -mod=readonly ./controller ./service ./model ./router` 通过。实际 DELETE 入口通过模拟清理失败验证停用、投递取消和关联删除整体回滚，再验证正常成功清理。独立只读审查和差异检查通过。未调用生产数据库或 Telegram；本轮仅修改共用后端，不改两套前端页面。

分享评估：NewAPIForDouDi 若采用相同工单回执，建议同步三天期限与停用清理，避免长期保留正文；NewAPIModifyByGang 仅在具有原通知编辑跟踪表时适用，普通通知无需照搬。未对兄弟仓库执行外部写入。
