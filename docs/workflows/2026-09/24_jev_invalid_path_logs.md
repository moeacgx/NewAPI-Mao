# Cloudflare Jev 错路径请求的使用日志隔离

## 问题和范围

用户将 Cloudflare Jev 渠道别名发到 /v1/responses，首轮分发没有可用渠道，产生渠道 0 的错误日志。
该分支在 middleware.Distribute 中直接终止，本来不进入模型广场 perf_metrics 采样；
两套前端均查询独立性能 API，不从错误日志回填性能数据。
用户要求此插件非指定路径的误用不写使用日志。保留 HTTP 错误、运行日志和鉴权，不更改计费、渠道或插件协议。

## 识别与安全边界

仅在当前活动插件包含 cloudflare-jev、当前授权分组/请求模型的启用候选非空且全部绑定该插件、
请求路径不属于其合法入口时，跳过分发阶段的使用错误日志。按实际渠道模型识别，支持任意别名；
不使用模型名包含 jev、错误消息文本或全局 model_not_found 规则。
合法入口由当前插件注册表与通用 /v1/task/plugins/cloudflare-jev 入口决定。
单分组、多分组和 Auto 使用同一请求授权范围；缓存与数据库候选均检查。

正确路径的失败、插件未激活/停用、未知模型/无候选、数据库故障、权限与并发错误均保留日志。
同名普通渠道混用时保守保留日志。指定渠道只在明确的插件路径不匹配处应用同一规则。
历史日志不删除。两套前端都从后端获得同一日志结果，无前端代码改动。

## 验证计划

用本地真实 Gin 分发路由、测试数据库和活动插件验证错误响应、日志行数、处理器未执行及性能样本不变。
覆盖缓存开关、自定义别名、Responses/Chat 错路径、合法原生/通用路径、未知模型、其他分组、
插件停用、其他插件、普通渠道混用、指定渠道、权限拒绝及并发边界。
测试超时 60 秒；不发起真实付费推理，不部署。

## 验证结果

真实 Gin 分发回归先复现 Responses、Chat、指定渠道和多分组错误请求仍写日志的红灯，
修复后在缓存开启和关闭两种模式验证：

- 自定义 decision-alias（不在插件 meta.models 中）可识别所属渠道；Responses/Chat、指定渠道、
  有序多分组和 Auto 的错路径请求保持错误响应且不新增使用日志。
- 未知模型、其他分组、模型权限拒绝、插件停用、其他插件继续写日志。
- 正确原生/通用路径的密钥不可用、正确路径并发超限继续写日志。
- 同名普通渠道故障、混合供应商的指定错路径保守保留日志；普通渠道成功分发不受影响。
- 请求未发生预扣，余额不变；分发错误前后独立模型性能摘要一致。

修复属于宿主日志入口，需要包含本修复的主程序；仅更新 Cloudflare 插件源码无法覆盖进入插件前的错误。
未修改前端模板、外部请求协议、费用和插件版本。没有删除既有数据或执行部署。

`go test -mod=readonly -timeout=60s ./middleware ./model ./router ./pkg/perf_metrics -count=1`
和相同包的 `go vet -mod=readonly` 均通过。
新增用例使用真实 Distribute 和数据库，末端为统计调用次数的本地处理器，不是实际供应商推理或生产部署验收。
