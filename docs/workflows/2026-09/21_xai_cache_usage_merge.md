# xAI 分段缓存用量一致性

## 现场与证据边界

.332 的 Grok Messages 调用已成功，但用户反馈同一对话多轮缓存很低。精确请求日志显示
输入 64,213、输出 125、缓存 128，缓存占比约 0.2%，计费使用上游路径；
普通输入 64,085 与缓存 128 分开计费，页面和账单数值一致。
同一渠道临近的 Chat/Responses 请求可达到高缓存命中，故不能推断该渠道完全不支持缓存。
现有日志未保存原始上游 usage 分片，该请求也没有对话归档；最终 128 不能证明低报缺陷在现场触发。

按同一用户/令牌查询临近 Messages 请求发现，渠道依次为 892 → 897 → 881 → 892，
缓存为 0/128；后续再次使用 892 时，输入 64,323、缓存 64,128（99.7%）。
这些请求均未记录亲和匹配。线上配置确认 Messages 亲和规则 `model_regex` 缺少 Grok，
而 Chat/Responses 规则包含 `^grok-.*$`。这是连续换渠导致缓存难以复用的直接配置证据，
优先补齐现有 Messages 规则；沿用 `metadata.user_id`、360 秒 TTL 及现有失败重试配置。
同用户/令牌本身不证明同一会话，原请求未归档，是否携带稳定 `metadata.user_id` 仍需后续真实调用日志确认。

## 已复现的实现问题

固定 .332 提交的实际 xAI handler 回归表明：逐块归一化会把别名提升为标准缓存，
影响后续字段优先级；较小的中间 prompt 会过早截断缓存；Claude 回包转换器对
input_tokens_details 的优先级与 xAI 结算不同，可能导致客户端和账单不同。
单块标准大缓存与后到的标准大缓存可正常保留，没有固定 128 上限。

## 方案与契约

- xAI 原始 usage 按字段存在性合并，缺失保留旧值，显式零覆盖同来源旧值。
- 缓存来源稳定优先级为 prompt_tokens_details.cached_tokens、input_tokens_details.cached_tokens、prompt_cache_hit_tokens；不按最大值猜测真实缓存。
- 原始聚合与用于输出的归一化副本分离；最终 prompt 收齐后才对最终缓存作非负/上界约束。
- 仅在 xAI 边界统一转换输入，确保 Claude 回包和 xAI 计费使用同一规范缓存值；不扩改其他渠道的通用协议语义。
- 不改变计费倍率、不回写历史账单、不增加数据库迁移，不凭缺失证据切换线上协议或制造缓存量。

## 验证计划

先红测，覆盖 JSON/SSE、各来源分片、显式零、标准与别名冲突、缓存先到及 prompt 后到、
客户端回包与结算一致性；单次 go test 使用 -timeout 60s。保持原生 OpenAI 流、
Messages 文本/推理/工具和 Responses 桥接既有回归。
修复能防止特定返回形态的缓存低报，但不会强制供应商产生缓存命中。
