# 复制令牌密钥被共享关键操作限流误伤

## 问题与证据

用户报告只点一次复制密钥，`POST /api/token/:id/key` 却返回 429。当前单条及批量读取
密钥均使用 `CriticalRateLimit()`，与登录、OAuth 状态、个人设置等共用按 IP 的 CT 桶。
该额度不等于复制次数；其他用户或其他操作可以先耗尽。

2026-09-21 线上只读日志核对确认对应单条密钥请求返回 429。三节点 CT 为 20 次/1200 秒，
GA 为 12000 次/60 秒。相关失败请求的同出口前 20 分钟存在几十至数百次登录请求，
最近一分钟 API 请求仅为个位数或十余次，与 CT 串扰相符。IP 只能关联出口，不能归属唯一用户；
本次未读取 Redis 桶的历史值，也未读取任何真实密钥或调用生产取密钥接口。

## 修改方案与契约

- 单条 `POST /api/token/:id/key` 与批量 `POST /api/token/batch/keys` 使用同一个按已认证用户 ID
  计数的专用限流桶。不同用户同 IP 隔离，同一用户切换 IP、令牌 ID 或单条/批量接口不能绕过。
- 默认每用户每 60 秒 60 次请求，批量仍最多 100 个 ID。独立环境配置
  `TOKEN_KEY_READ_RATE_LIMIT_ENABLE`、`TOKEN_KEY_READ_RATE_LIMIT`、`TOKEN_KEY_READ_RATE_LIMIT_DURATION`
  分别默认为 true、60、60；非正额度和越界窗口回退默认，窗口最大不超过内存桶清理周期 1200 秒。
- 请求链为 GA → UserAuth → 禁止缓存 → 取密钥专用限流 → 控制器密钥归属检查，不增加管理员全局豁免。
  登录和其他关键操作保持原限流配置，CRITICAL_RATE_LIMIT 不再控制取密钥。
- 专用限流超限仍返回 429 和 Retry-After，取密钥成功及该限流错误均禁止缓存；Redis 故障保持失败关闭。
  多节点使用共享 Redis 时共用用户计数，纯内存模式仍按进程计数。
- 成功响应、鉴权、客户端 API Key、批量归属过滤和 100 个 ID 上限保持，无数据迁移。
- Default 与 Classic 均调用这两个后端接口，复制按钮已有同 ID 在途去重和页面缓存，直接 429 不自动重试；401 刷新成功后允许重放。复制之外的聊天页仍可能主动读取密钥，Default 聊天 Query 沿用通用重试规则，这些请求会计入该用户额度。本次不修改两套前端。

## 验证计划

先用真实 API 路由复现 CT 耗尽后首次复制被拒，再覆盖 Redis 和内存的双向隔离、
同 IP 不同用户、同用户跨 IP/凭证与单条/批量共享、窗口恢复、禁用配置、无身份及越权、
批量上限与 GA 保留。测试超时 60 秒，另执行受影响包回归、静态检查、构建和文档检查。

## 兼容与回滚

现有前端无需更新即可使用新计数逻辑；无需清理线上 Redis，旧 CT 桶自然过期。
回滚会恢复共享 CT 的误伤风险。其他工作树中存在更大范围的未提交限流方案，本任务不覆盖其文件，
只修复本次取密钥问题。部署状态以后续交付记录为准。

## 验证结果

- 原实现真实路由在 Redis 与内存模式均复现共享 CT 耗尽后首次复制 429；修复后返回正确所有者密钥且禁止缓存。
- 用户额度隔离、PAT/Session 与跨 IP 共用、单条批量共用、CT 双向隔离、Retry-After、Redis 窗口恢复通过；定向测试重复 2 次通过。
- 无效/缺失鉴权、读取他人密钥、批量所有权过滤与 101 个 ID 拒绝均保持。独立开关不关闭 GA，关闭 CT 不关闭取密钥专用防护。
- 测试夹具显式初始化数据库方言列名，内存计数使用唯一且合法的 IPv6 来源；不读取或写入生产密钥。
- `go test ./common ./middleware ./router -count=1 -timeout 60s` 全包通过，受影响包 `go vet`、根模块 `go build ./...`、Markdown 格式与差异检查通过；独立只读审查未发现阻断问题。
