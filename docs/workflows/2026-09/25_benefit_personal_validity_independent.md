# 福利券个人有效期与活动窗口分离

## 问题与目标

管理端把活动领取窗口设置为一天、个人有效期设置为 168 小时，领取后的券仍显示在活动结束时失效。原因是领取代码把券到期时间计算为 `min(领取时间 + 个人有效期, 活动结束时间)`，使活动结束时间覆盖个人配置。此前工作记录把该公式当作契约；本次按实际产品配置修正。

## 范围与契约

- `starts_at <= now < ends_at`、活动状态及领取条件仍决定能否领取。
- 成功领取的券设置 `expires_at = claimed_at + personal_valid_seconds`；活动自然结束或管理员提前结束，只停止新的领取，不截短已领券。管理员选择全部作废仍按原规则作废券。
- 券按当前请求中的实际到期时间跨券抵扣；金额、已用额度及原有流水不因修正公式变化。
- API 路径和字段、SQLite/MySQL/PostgreSQL 数据模型保持不变；Default 和 Classic 均直接展示服务端返回的 `expires_at`，不需调整日期格式。

## 线上历史券

2026-09-25 只读审计确认活动 8「中秋福利 Grok」设置个人有效期 604800 秒，12 张已领券均被截到活动结束时间，仍处于 active 且重新计算的期限尚未到。拟在生产新代码就绪后按每券领取时间加 604800 秒补正这 12 张券，仅修改 `expires_at`，保留原金额、状态、余额、已用额度和流水。执行前须再次核对活动配置、券状态、笔数及是否有其他领取，备份变更前行，事务内以行锁和条件更新防止并发覆盖；完成后逐条核对新到期时间及不变量。

更早活动中符合相同截断特征的券，按个人有效期重新计算后均已经过期，不予复活。未来若出现新的未过期受影响券，须再次审计后单独处理，不对全部历史券无条件延期。活动结束时间不改动，历史 `expire`、`void` 和消费流水不重写。

## 验证计划

- 模型回归覆盖领取后到期时间越过活动结束、活动结束后券仍可使用、领取窗口边界与旧活动配置快照。
- 运行 `go test ./model ./service ./controller -count=1 -p 1 -timeout 60s`；检查格式和 `git diff --check`。
- 在 SQLite、MySQL 5.7、PostgreSQL 15 复核福利券定向回归；发布时确认双前端构建与生产逐节点健康。
- 生产只读核对活动 8 的所有已领券、截至时间、金额及状态，修复后验证领取/到期显示和已有有效券扣费。无付费模型测试时不宣称新券实际扣费已在线验证。
