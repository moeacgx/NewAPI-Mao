# 上游模型校验接入 Codex 响应头证据

## 目标与方案

当前守卫只消费响应正文模型声明。当正文仍声明允许模型、Codex `x-codex-safety-buffering-faster-model` 响应头声明其他模型时，异常会漏检。本次参考团队 tokens-pro-gang 的头部信号，在宿主现有 HTTP 请求链路采集这项模型声明，接入现有守卫。

只接受成功 HTTP 响应的单一、非空、合法模型名，限 255 字节；不消费客户端同名请求头。拒绝重复值、逗号合并值、内部空白、控制字符和无效 UTF-8。正文模型和响应头模型分开保留，不能把头部缓冲模型冒充最终回答模型。

## 数据与策略契约

- 原有 `SetUpstreamResponseModelName` 保持正文日志含义；内部模型观察回调增加来源 `response_body` / `codex_faster_model`。
- faster-model 按原规则的允许模型列表精确匹配。不匹配立即进入现有连续容错、持久化记录和通知流程；同请求同渠道最多累计一次，后续正文匹配不撤销已观察异常。
- 头部匹配本身不证明完整响应正常，不能单独清零连续异常；仍由正文匹配按既有请求收尾语义清零。
- 保留检测总开关、规则开关、分组、请求模型、渠道白名单、并发版本校验及人工恢复约束。
- safety-buffering 标志、turn-state 长度与 Plan 不作关渠依据，也不采集 turn-state 内容。
- 记录新增可空文本列 `detection_source`，历史空值读出为 `response_body`；沿用 GORM 兼容 SQLite、MySQL、PostgreSQL 的加列迁移。通知对头部证据明确展示来源。
- 管理员消费日志的 `admin_info` 增加 `codex_faster_model`，正文 `upstream_response_model_name` 不被覆盖；普通用户继续通过现有 admin_info 脱敏。
- 检测完全由主程序实现，现有外置模块 0.2.1 继续配置规则、白名单与容错并读取原接口，不修改双模板页面、不增加模块能力声明、不发布新模块包。来源可由记录接口、原因和通知追溯。

## 验证计划

真实本地 HTTP 响应覆盖头部采集，验证不信任客户端请求头、错误 HTTP 状态不观察、畸形值不误判。守卫回归覆盖正文正确但头部不匹配、同请求去重、白名单、关闭配置、连续阈值、成功正文清零、仅匹配头不清零、重试换渠、记录来源与通知。补充旧表升级和历史来源回显，核对既有模块配置与记录接口保持兼容。

## 交付边界

识别依据是上游模型声明及路由信号，不是底层模型身份的独立证明。中间代理未透传响应头时无法还原这项证据。本功能通过更新主程序生效，继续使用现有模块及配置。后续已按用户授权发布 .330 并逐台更新 maolaoapi 三应用，见[部署记录](21_maolaoapi_codex_header_330_deployment.md)；外置模块未升级。

## 本地验证

- 已用真实本地 HTTP 服务器覆盖成功响应采集、客户端伪造同名头不被采纳、上游错误状态不参与、正文不被消费或改写。
- HTTP 请求链路接入真实 Responses JSON/SSE 解析器，正文仍声明允许模型、响应头声明其他模型时均能在正文解析前按规则禁用渠道，当前响应正常完成且正文模型保持原样。
- relay/common、relay/channel 全包测试和 service/model 的守卫、日志生成、普通用户日志脱敏定向测试通过，均设置 `-timeout 60s`。
- 守卫回归覆盖连续阈值、同请求多证据去重、正文匹配不撤销头部异常、匹配头不单独清零、白名单与开关/分组/请求模型范围。
- SQLite 旧表升级、历史 NULL/空字符串来源回退、新记录来源持久化与通知摘要通过；MySQL/PostgreSQL 未执行真实数据库升级验收。
- 独立只读审查确认公共请求入口覆盖 NewAPI/OpenAI/Codex 与 Responses 转换路径，未发现阻断问题。Default、Classic 及模块包没有修改，本次不宣称新增模块详情界面或 SSE 头部透传。
- 共通过 203 项顶层测试（relay/common、relay/channel 157 项；service/model 定向 46 项），另含各表驱动子用例。受影响包 `go vet`、根模块 `go build ./...`、修改文档格式和 `git diff --check` 通过。
