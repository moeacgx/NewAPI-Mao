# 当前连接慢刷新过期提示修复

## 问题与目标

用户观察到多个客户端窗口同时工作时，当前连接面板有时只显示一条。线上只读采样期间，目标账号在 Redis 中登记了 3 至 4 条进行中请求，续租正常；前端没有按模型或令牌合并请求的逻辑，因此尚未复现稳定漏计。

已确认页面在轮询请求进行中继续把旧快照标记为“实时更新”，直到请求失败或超时才提示异常。后端每 2 秒发布，页面每 2 秒轮询，正常变化可延迟约 4 秒。此次修复目标是让快照新鲜度可见，避免慢查询期间旧数字被误认为实时数据。

## 范围与方案

- Default 与 Classic 当前连接预览和抽屉均在轮询时显示刷新状态。
- 前端记录最近一次成功响应时间；快照超过 5 秒未更新时标记过期，即使下一次请求仍在等待。
- 请求失败时保留最后快照并显示已有错误提示，成功刷新后恢复新鲜状态。
- 保持 API、Redis 租约、请求生命周期、摘要口径、筛选和计费行为不变。
- 线上采样证明查询时 Redis 中有多条请求，但没有与网页同一时刻的快照证据，因此本次不声称已定位所有偶发少显原因。
- 单节点无法判断其他节点是否持续活着但 Redis 发布失败；修复该集群级盲区需要节点健康/发现契约，本次不以错误的局部信息伪造完整性。

## 安全、兼容与数据生命周期

仅改前端状态展示，不新增接口、权限、存储字段、数据库迁移或持久化数据。保留已有的 10 秒查询超时、2 秒轮询、页面隐藏暂停和错误恢复行为。过期提示表示最后成功快照可能不完整，不改变请求是否活动的服务端判断。

## 测试计划

- 先添加 Default 与 Classic 的慢请求回归测试，断言旧快照仍在时显示刷新状态，超过 5 秒显示过期状态，成功后清除过期提示。
- 运行两套受影响组件测试、Default 类型检查和前端 lint/格式检查。
- 后端无需变更；以既有当前连接测试和契约检查确认接口未变。
- 代码审查时检查本人和管理员按用户查询路径都复用该状态展示。

## 实施结果

Default 与 Classic 的连接预览和抽屉都会显示正在刷新的状态。若最近一次成功快照已超过 5 秒，查询仍在进行时提示“数据延迟，显示上次状态”；如果请求结束后快照仍超过 5 秒，则标记状态过期。查询失败继续显示错误与重试入口。Default 七种语言与 Classic 八份语言资源均补充了延迟提示文案。

验证结果：Default 连接组件测试 11/11 通过；Classic 连接组件测试 22/22 通过。两套慢刷新回归均验证请求持续等待时旧连接仍可见、5 秒后提示延迟、成功刷新后恢复。`git diff --check` 通过。Classic 测试运行时有项目既存 Browserslist 数据过旧与 `TimeoutNaNWarning` 提示。

本次仅改变前端对已有快照的状态标记，不增加后端观测能力。若不同请求落在不同应用节点且某节点 Redis 发布失败，当前查询接口仍可能看不到该节点的连接；本次页面提示不能证明集群快照完整，也不能替代后续对跨节点发布/部分失败契约的修复。
