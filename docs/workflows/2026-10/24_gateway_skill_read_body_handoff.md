# 云端技能正文读取与激活核验

## 问题与范围

用户在 zzapi 操练场先列出已安装技能，再要求阅读 `rev-struct`，回答却声称没有技能读取工具，
要求用户另行粘贴 `SKILL.md`。失败回答同时显示该技能的网关读取徽标，不能仅凭模型自述判断读取失败。
用户随后反馈单技能切换为渐进式披露后，要求“激活”可以得到符合正文的回答。

本项先检查共用后端的正文传递及真实读取审计，再判断是否需要修复，不预设合集结构存在缺陷。
本次只做核验与文档补充，没有修改实现、数据库或站点配置，没有重新部署。

## 实现边界

- “激活 XXX”是模型理解的自然语言请求，没有独立的字符串命令或持久激活状态。
  私有发现阶段调用 `newapi_skills_read` 后，网关才会真正读取授权正文。
- `GatewaySkillSession` 每次请求创建，不跨请求或跨组重试复用。`FinalBody` 重新校验当前令牌、
  实际分组、安装、发布状态和版本，仅将实际读取且内容未变化的文件页加入本轮正式请求。
- 因此正文进入当前模型输入上下文，不会自动下载到客户端文件系统，也不会自动回写客户端的
  完整聊天历史。后续需要该技能时仍按需读取；没有“激活一次，后续会话永久保留且不再计费”的机制。
- 目录查询只返回元数据；单独列出技能不表示已经读取正文。正文读取受现有分页和每请求预算限制，
  一次读取某个技能不代表整包所有文件都已加载。
- `网关云端 Skills` 徽标来自本轮实际非空文件页的授权重验结果，证明文件已装载，
  不证明模型遵守了正文、执行了技能步骤或拥有技能引用的客户端工具。

## zzapi 实际核验

沿用原有 Default 操练场连续历史、API 令牌模式和 `deepseek-v4.1-flash`，要求实际读取
`rev-struct/SKILL.md`，仅列出正文中的章节与具体说明，不执行其中操作。

- 页面回答明确更正之前的拒读自述，列出了正文特有的预检查、导出目录、函数文件格式及
  结构恢复步骤，显示 `网关云端 Skills：rev-struct`。
- 使用 CloudSSH 对 zzapi 日志只读查询，正式生成记录 `24885352` 的 `gateway_skills.files`
  包含 `rev-struct`、版本 `3`、`SKILL.md`、偏移 `0` 和 `5891` 字节，发现轮也记录同一文件页。
  与页面报告的全文范围一致，证明合集子技能的正文读取和正式装载链路已经工作。
- 同批审计中，单技能与另一个合集子技能也分别有实际正文读取记录；后续另一次请求的
  `files` 为空，符合按请求重新判断、没有持久激活状态的实现。
- 审计不读取或输出令牌密钥、凭据、完整日志负载及用户私有技能正文。

旧拒读回答与实际装载徽标不一致，现有证据更接近模型对自身读取能力的误判，不能据此认定
网关没有传正文。当前已实测可读取正文，本次不添加强制全包加载或会话缓存。
本次真实供应商核验仅覆盖上述 Default 请求，不宣称所有模型或协议都会正确理解“激活”。

## 验证与共享影响

核对 `NewGatewaySkillSession`、`Execute`、`FinalBody` 和审计路径；仅文档变更，无需重跑
程序构建及后端测试。修改文档的 Prettier 检查、新增两处相对链接检查和 `git diff --check` 已通过。

本项没有新增跨项目接口或部署契约，不触发兄弟仓库通知。
`NewAPIForDouDi` 和 `NewAPIModifyByGang` 若采用渐进式读取，都值得同步此处的上下文与计费
说明，以免将自然语言“激活”误认为持久会话状态；不需要同步本次实现补丁，因为没有代码变更。
