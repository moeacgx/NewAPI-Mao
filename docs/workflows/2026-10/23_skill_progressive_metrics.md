# 渐进式技能轮次与渠道重试统计

## 问题与范围

网关内部技能读取每轮都记录渠道尝试和上游调用，原来的尝试序号递增会把正常读取轮次计入
`NonFirstAttemptCount`，渠道分析页面因此错误展示重试次数。最终请求样本的 `RetryCount`
也直接使用了全部模型轮次减一。

指标实现只修改 `service/channel_metrics_lifecycle*.go`。另在 `controller/gateway_skills_retry_test.go`
通过真实鉴权、分发和 Relay 链验收跨分组重试。网关调用点和最终流式标记恢复由运行时任务处理。

## 方案与兼容性

- 为网关内部读取提供明确的指标入口，启用当前请求的多轮模式。
- 每个模型轮次仍独立记录用量、时延、上游状态，保留唯一序号定位失败事件。
- 多轮模式按外层 `RelayInfo.RetryIndex` 判断真实渠道重试；同一外层尝试的后续模型轮次不重复计数。
- 最终请求样本只记录实际开始的渠道重试数。未使用该新入口的调用保持原有尝试计数语义。
- 不改变鉴权、资金来源、计费、结算或退款；不增加数据表和配置。

## 验证计划

覆盖三轮读取加最终生成没有重试、读取失败后真实重试、重试后不再装载技能，以及普通渠道先失败后
才进入技能读取的场景。验证尝试和上游调用次数、用量仍保留，渠道重试仅计实际外层重试。
执行 `go test ./service -run ChannelMetric -count=1 -timeout=60s`、格式和差异检查。

跨分组端到端场景使用自动分组令牌，第一组读取主文件和引用资源且成功结算，最终生成返回 500，
再由真实分发选择第二组。第二组不在技能白名单中，必须恢复客户端原始正文和工具，不能带入第一组
已读正文、目录或内部工具结果；钱包、令牌与消费日志只保留成功读取轮次和重试成功的最终生成费用。
上游由本地 HTTP 服务模拟，站内鉴权、分组白名单、路由、计费及日志使用实际实现。

## 验证结果

- 渠道指标定向测试通过，包含现有非技能调用的生命周期回归。
- 新增六组确定性场景，验证三轮技能读取加最终生成的重试数为零，失败后跨渠道重试只计一次，
  以及无技能渠道与技能渠道之间切换、连续两次真实重试的统计口径。
- 每个读取和生成轮次仍计入尝试、上游调用和用量；第三轮读取失败保留独立失败序号，
  不把聚合重试标记当作失败事件标识，后续成功后也不误标为最后一次尝试。
- 跨分组端到端回归通过：第一组成功读取主文件及引用资源，共三次模型调用；最终生成返回 500 后，
  通过实际自动分组重试切换到有独立渠道的第二组。第二组不在技能白名单中，只调用一次最终生成，
  上游消息与工具恢复为客户端内容，没有第一组的技能目录、已读正文或私有工具结果。
- 钱包与有限令牌余额均从 10000 变成 9600，恰好四条消费日志：第一组三次读取和第二组一次最终生成
  各 100，失败的第一次最终生成没有额外收费。日志分别保留实际分组、渠道及用量，第二组没有技能审计残留。
- 执行 `go test ./controller -run TestGatewaySkillsAutoRetryReloadsActualGroupAndPreservesSettledUsage -count=1 -timeout=60s`
  通过。该回归覆盖非流式 Chat Completions、按次定价及钱包资金来源；未调用真实供应商。
- `gofmt` 和 `git diff --check` 通过，工作记录格式检查通过。
- 本项没有调用生产接口、发布或部署。最终流式标记、网关调用点和其它资金来源由集成任务验收。
