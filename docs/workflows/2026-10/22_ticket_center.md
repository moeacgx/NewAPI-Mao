# 双模板工单中心实施记录

## 目标与基线

- 用户要求个人工单中心、管理员额外工单管理、控制台浮窗创建、通知中心可添加工单通知；已明确 Default 与 Classic 两套模板均需实现。
- 用户纠正分支后，从最新远程默认主分支 origin/custom-main 的 dea7b5d18 创建 feat/ticket-center-20261022，开始实现前 behind/ahead 为 0/0。
- 两套前端分别使用同一远程基线的独立工作树；后端和最终整合由主 Agent 写入。没有生产操作、推送或发布。

## 方案与实施顺序

契约先记录于[工单专题](../../developer/tickets.md)。后端先写归属、生命周期、输入边界、分页与通知事务回归，观察缺失实现失败后补模型；前端在固定 API 契约下独立实现。

1. 增加 Ticket/TicketMessage，两条迁移入口同时登记；复用 GORM 和跨库行锁 helper。
2. 增加用户与管理员独立路由、tickets read/write 权限，复用认证、禁缓存、限流和管理审计。
3. 注册四类核心通知事件、默认模板、变量样例；工单正文不进入外发负载。
4. 双模板实现个人与管理列表、会话、创建、关闭重开、浮窗、侧栏配置和语言资源。
5. 整合后运行后端、前端测试与类型/lint/build，检查格式和文档链接。

## 已发现并修复的边界

- 单次 JSON Decode 不读取整个请求体，短 JSON 后追加超长空白可能绕过 64 KiB 限制。已先用回归复现 200 写入，再改为限长完整读取和 common.Unmarshal；同时拒绝多段 JSON，覆盖 ContentLength=-1。
- 管理员的个人入口不能因账户角色变为全局查询或管理员回复；API 范围由固定路由构造，归属由会话 ID 决定。
- 状态事件不能只按工单 ID 和状态去重；使用递增版本，保留重开后再次关闭的通知。
- 通知表未就绪沿用可选语义，需要明确不补历史通知；有订阅时入队错误必须回滚工单和消息。
- 两套模板使用相同 personal.tickets / admin.ticket_management 侧栏键，服务端新用户默认配置同步增加，避免切换模板后开关失效。
- Classic 保存中禁止关闭详情，失败保留草稿；列表、详情、浮窗和权限在切换账号后忽略旧请求。
- Default 的 mutation 回调不会因组件卸载而取消；先复现 8 项账号切换失败，再按提交身份隔离成功、失败及查询缓存更新，避免旧账号结果影响新账号弹窗。

## 用户提交后的单次自动回复（2026-10-24）

根据后续需求，增加管理员工单自动回复配置。配置通过
`GET/PUT /api/ticket-admin/automation/auto-reply` 管理，读取需要 `tickets:read`，保存需要
`tickets:write`；内容最多 10000 个 Unicode 字符，启用时不能为空，默认关闭。

配置以 JSON 保存在主库 `Option` 的 `TicketAutoReplyConfig` 键。用户创建工单时，服务端在创建
事务内追加一条 `admin` 消息（系统作者 ID 为 0）；事务回滚不会留下自动回复，配置关闭时不会
写入，配置变更也不会重新处理历史工单。自动消息不单独发送管理员回复通知，仍只产生一次
`ticket_created` 事件，避免通知重复。

模型测试覆盖默认关闭、字段校验、配置持久化、启用时仅追加一条系统回复及关闭后不追加回复。
尚未进行 MySQL/PostgreSQL 实例验收，也未部署或发送真实通知。
