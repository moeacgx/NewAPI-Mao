# dev 整合与 zzapi 验证部署

## 目标与范围

将当前稳定基础及 PR #301、#302、#303、#304、#305、#307、#308、#309、#310
整合到 dev，保留 dev 原有历史。不包含主工作区未提交的订阅扣费顺序修改。
整合过程保留各功能提交，并在组合基线上修复审查发现的问题和补充回归。

## 部署契约

- dev 推送运行后端、独立 relaykit 和前端 CI；仅检查成功后构建 amd64 开发镜像。
- 开发镜像使用 `ghcr.io/moeacgx/newapi-mao:dev-<完整提交 SHA>`，版本为
  `dev-<短 SHA>`，带源提交标签。不创建正式 Release，也不更新稳定 latest 镜像。
- 只部署 zzapi 的三个应用服务，按节点顺序检查健康、版本、镜像和静态资源。
- 先保存 Compose、环境配置、运行状态和 PostgreSQL 备份；不重建 PostgreSQL/Redis。
- 回滚使用备份中的旧 Compose 与固定旧镜像，逐应用恢复。

## 补充修复计划

- 公共预置上游对应的空脱敏集合必须显式保留作用域语义，避免退回旧版全量域名脱敏。
- Sub2API 仅把无正限额订阅的 `remaining=-1` 视为无限哨兵；真实钱包负值和有限余额正常更新。
- Realtime 测试必须等待升级连接对应的处理器完成，再恢复全局数据库和删除临时目录。
- DeepSeek 独立端点按管理员配置的按次价格预扣与结算，保留审计和统计。
- 通知与拖拽修复及回归随相应专题记录更新。

## 验证与证据

Go 测试单次设置 `-timeout 60s`，独立 relaykit 使用 `GOWORK=off`。
前端执行类型检查、相关回归和构建。部署结果、固定摘要与验收边界在完成后补充。
