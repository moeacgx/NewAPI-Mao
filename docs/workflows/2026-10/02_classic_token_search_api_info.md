# Classic 令牌搜索与 API 信息入口

## 目标与范围

修复 Classic 令牌列表中名称和密钥只能完整匹配的问题，并在“添加令牌”同一操作区提供 API 地址入口。随后根据用户反馈，将新版 Default 的桌面表格与手机卡片展示移植到 Classic。Default 仅作为移植来源，生产源码不修改；初期对照的是 custom-main 的较旧 Default，完整移植来源为下文固定的 upstream ref。

## 搜索契约

- `/api/token/search` 继续接收 `keyword`、`token`、分页参数，并支持可选 `status`；前端不拼接 SQL 通配符。
- 普通非空输入按字面量执行包含匹配，`%`、`_` 和 `!` 继续按字面量转义，避免用户输入改变查询语义。
- 显式通配符仍遵循现有校验和高令牌量保护；空输入不增加过滤条件。
- 查询仍使用 GORM `LIKE ... ESCAPE '!'`，兼容 SQLite、MySQL 和 PostgreSQL。

## API 信息入口

- 复用 `/api/status` 返回的 `api_info_enabled` 和 `api_info` 数据，不新增接口或持久化字段。
- Classic 顶部操作区增加轻量 Popover，展示路由、地址和说明，并支持复制地址。
- 配置列表为空或面板被禁用时，按新版 Default 回退到 `server_address`，再回退当前域名；请求失败保留错误提示。

## 验证计划

- Go：名称前缀/中间片段、密钥片段、特殊字符转义、分页和无结果搜索回归。
- Classic：API 信息入口、空状态、复制操作、桌面/移动布局，以及原有令牌标签选择测试。
- 执行受影响 Go 测试、Classic compat 测试、Prettier、ESLint 和 `git diff --check`。

本地验证覆盖桌面与 390px 窄屏、API 信息浮窗、名称和密钥包含搜索、启停、标签直接弹出选组、

## .346 后的 Default 页面直接移植

用户线上反馈长令牌名称与状态重叠，并明确要求直接采用新版 Default 令牌页面。
根因是上一版 Semi Table 使用固定列宽，而名称被设为不换行且未限制溢出；
Classic 的旧分组渲染器也没有采用 Default 的 StatusBadge / GroupMultiplierBadge。

本次以与用户提供 DOM 一致的 `upstream/main@789c97019` 为移植基准：
`features/keys`、`components/data-table/core/table-sizing.ts`、`data-table-colgroup.tsx`、
`components/ui/table.tsx`、`status-badge.tsx`、`group-badge.tsx` 与 `styles/theme.css`。
只移植 Classic 令牌列表视图；Default 的 React19/BaseUI/Tailwind4 框架不整套引入 Classic。
保留 Classic 请求、鉴权、按需取密钥、分页及已经完成的多分组创建/编辑弹窗。

- 原生 table 使用 Default 的自动布局、可见列宽度总和作为最小宽度、百分比 colgroup；
  长名称撑开所在列，内容在表格容器内滚动，右侧操作列保持固定，不覆盖相邻单元格。
- 页面按可用视口高度填满，表头与分页可达；少量数据不把列表边框压缩到内容高度。
- 手机端采用 Default 的卡片顺序，长名称自动换行；状态、密钥与操作、分组、额度、限制、时间和过期信息分别排布，模型/IP 限制支持点击详情。
- 字体、状态、分组、倍率、模型/IP 限制、额度和时间按新版 Default 的组件语义移植，
  展示名称仍来自 `group_details`，提交标识不变，不使用 Classic 旧命名色渲染器。
- 新版 Default 已有 API 地址入口：采用配置列表，未配置时回退 server_address / 当前域名。
- 验收必须包含真实截图同类长名称、超长连续字符串、隐藏列、空列表、窄屏/暗色，
  用单元格几何断言验证没有跨列重叠，而非仅检查页面宽度。

本次仅前端变更，无数据库迁移；通过验证后继续 PR、合并和原三节点滚动更新流程。

## .347 后历史语言标识导致令牌页崩溃

生产用户反馈令牌页进入 ErrorBoundary。只读核对账号设置确认历史语言为 `zhCN`；
使用线上 .347 实际发布包、模拟登录资料中的相同语言设置，复现
`RangeError: Invalid language tag: zhCN`，堆栈落在新增相对时间组件。
既有 normalizeLanguage 处理 zh_CN / zh-CN，但未处理历史 zhCN / zhTW；
上一轮演示与单测固定使用规范语言，遗漏该兼容分支。

修复计划：统一语言规范化兼容历史别名；时间组件在 Intl 边界选择已支持的语言，
异常语言回退既定中文，不让显示设置导致整页崩溃。保持数据库设置及 API 契约不变。
先补失败测试覆盖历史别名、异常语言、正常多语言，再验证完整生产构建的登录态页面，
通过后发布 .348 并逐节点更新。

### 历史语言修复验证

- 用户控制台提供的首条异常与实际 .347 发布包复现一致，确认根因为 `zhCN`。
- `normalizeLanguage` 兼容 `zhCN/zhTW`；时间组件将规范化结果限定为项目支持语言，异常语言回退 `zh-CN`。
- 时间组件兼容测试 19 项通过；独立复审亲自重跑 19 项通过，结论 approve。
- 令牌页测试 7 文件、38 项通过（49.50 秒）；合并分组测试的两次执行在 60 秒收集上限终止，没有作为通过证据。
- 完整压缩构建通过本地 preview 验收，保留 localStorage 与用户接口中的历史 `zhCN`，1780px/390px 页面均显示令牌、分组显示名称及相对时间，控制台无异常，页面无横向溢出。
- 涉及三个源码/测试文件的 ESLint、Prettier 通过。本轮不改 Default、依赖、数据库账号设置、令牌或计费/鉴权契约。

浏览器采用完整发布构建和虚构 API 数据，不使用用户凭据；生产新构建仍需以同样历史语言资料复验。
