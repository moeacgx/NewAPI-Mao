# 渠道优先级拖拽排序

## 目标

在 Default 渠道管理页提供可撤销的拖拽排序，让管理员能够直观看到并调整渠道优先级，同时保持原有筛选、分组和渠道能力排序契约。

## 交互范围

- 仅在按优先级排序、未启用标签聚合且拥有渠道写权限时启用拖拽模式。
- 表格和卡片视图共用拖拽句柄；支持键盘方向键移动，Escape 取消预览。
- 拖拽释放前显示目标优先级预览，释放后保存；保存失败可撤销并显示冲突提示。
- 使用 revision 做乐观并发控制，检测到其他管理员已修改时要求刷新后重试。
- 每次手势开始时记录用户可见渠道的 `{id, priority}`，提交前与本次 GET 返回的
  排序快照逐项核对，再使用该快照的 revision 提交；优先级变化或可见渠道缺失均
  要求刷新重试，不能把旧目标与新 revision 组合覆盖其他管理员的修改。
- `null` 与未返回的 priority 统一为 `null`；渠道 ID 缺失单独判冲突，不能视为
  空优先级。筛选范围外的渠道仍由服务端 revision 保护。
- 渠道优先级变化同步到对应的 `ability.priority`，保持能力路由选择一致。

## API 契约

- `GET /api/channel/priority/order` 返回当前 revision、可排序渠道和变更信息。
- `POST /api/channel/priority/reorder` 接收 revision、源渠道、目标渠道和位置（`before`、`after` 或 `same`），并返回新的排序结果。
- revision 不匹配、目标不在可排序范围或请求超出权限时返回明确错误，客户端保留当前列表并提示用户。

## 权限与数据库

查询要求 `ChannelRead`，重排要求 `ChannelWrite`。重排事务使用数据库行锁和 revision 校验，兼容 SQLite、MySQL 和 PostgreSQL；优先级使用既有整型字段，不改变渠道 ID、分组或计费标识。

## 2026-10-18 并发保护回归

基线已保存手势开始时的可见快照，并在提交时检查优先级，但原比较使用
`Map.get(id) ?? null`，把“不存在此渠道”与“此渠道优先级为空”合并，导致空优先级
渠道删除后仍可能提交旧目标。修复须先检查 ID 存在，再归一化比较优先级。
本地检测到冲突时直接显示既有“优先级已变化，请刷新后重试”提示并刷新列表，避免
通用错误处理将本地冲突退化为没有原因的报错。

通过真实 Hook 与 API 边界覆盖旧列表配新 revision、源/目标渠道缺失、
空值归一化和冲突后的列表失效刷新；跨视图用例必须通过带可访问名称的按钮真正切换
卡片与表格，禁止找不到按钮时跳过关键断言。共享视图按钮复用既有翻译作为
`aria-label`，无需新增翻译。范围仅为 Default，Classic 不在本次需求内。

验证结果：

- 修复前新增测试稳定复现两个空优先级渠道缺失场景仍发出重排 POST；三个原有
  跨视图用例改成强断言后均因视图按钮没有可访问名称而失败。
- 修复后 3 个相关 Vitest 文件共 36 个用例通过，包含 7 个 Hook 回归和表格/卡片
  各自拒绝旧目标并显示其他管理员最新列表的真实页面路径。
- 前端 app 与 node 配置的 TypeScript 检查通过；修改文件的 oxlint、oxfmt、Markdown
  Prettier 检查及 `git diff --check` 通过。Bun 不在本机 PATH，使用现有依赖的
  Node CLI 和 tsgo 原生入口运行等价检查，没有安装或更新依赖。
- 基于本地集成分支 `c97074005` 验证；未推送、部署或操作生产环境。Vitest 的
  jsdom 环境提示 `scrollTo` 未实现，相关交互断言均通过；这不代表实际浏览器验收。
