# 技能渐进式披露改造草案

## 状态与目标

2026-10-23 用户明确要求渐进式披露。本记录为设计草案，尚未实现、发布或部署；
Agent 接入方式正在确认。现有 ZIP、仓库和商店导入只是包来源，不能代替运行时按需读取。

目标是先让模型发现技能名称与适用场景，选中后读取该技能的 SKILL.md，
再按需读取其中引用的资料。合集作为安装包管理，内部技能独立发现与激活。

规范依据：[Agent Skills 格式](https://agentskills.io/specification)及
[客户端接入指南](https://agentskills.io/client-implementation/adding-skills-support)。
规范区分目录、指令、资源三层；当前项目的 32768 字节限制属于实现策略。

## 已核实的现状

- `model/prompt_template.go` 限制单模板正文 32768 UTF-8 字节，令牌启用正文合计 65536 字节。
- 导入的单个 SKILL.md 剥离 YAML 元数据后校验正文；限制不是字符数，也不是原文件字节数。
- `model/prompt_bundle.go` 将合集内所有正文拼接为一个模板，包含标题与分隔符的最终总量也受
  32768 字节限制；不是每项 32768 字节后可以无限合并。
- `service/token_prompt_runtime.go` 在每次请求选定实际分组后读取全部命中正文并注入。
  这不是只在对话首轮注入，也不会自动在 Agent 本地安装文件。
- 当前子技能只有标题和正文，缺少独立描述、稳定身份、相对路径和资源索引。
  导入器跳过引用资料及脚本，无法在后续按路径读取。
- 用户页面和安装 API 只提供摘要，管理员接口才提供正文；仓库没有现成的 MCP 服务端。

## 目标数据与加载边界

1. 发现：每个技能保存稳定身份、名称、描述、版本及所属安装包。只向模型提供当前可用的
   名称和用途，不带任何技能正文。描述用于判断适用场景，缺失时要求管理员补充后才能发布。
2. 激活：模型选中某个技能后，读取该版本 SKILL.md 正文和引用资源目录，其他技能正文不返回。
   同一名称来自不同安装包时使用稳定身份区分，不能用展示名称或数组下标作为授权身份。
3. 资源：保存技能根目录下的相对路径，按需单独读取支持的文本资料。
   路径必须规范化，拒绝越界、符号链接与包外引用。首期不提供服务器端脚本执行环境。

导入保留各技能自己的 YAML 名称、描述和资源路径，不再为了渐进式运行时生成全部正文的拼接副本。
单文件大小、包总量、技能数量、单次返回量和目录上下文预算分别设限，不能继续把整个合集
当作一份 32 KiB 系统提示词；具体新阈值须随接口和存储方案确定并记录。

普通提示词仍可使用始终装载方式，Skills 使用渐进式方式。老模板和老安装关系不能无提示地
改变行为；转换时保留管理员已有正文，并要求为缺失描述的子技能补全元数据。
旧版本数据库或回滚程序不能把渐进式包误认为已完整支持的普通提示词。

## Agent 接入方案

### 远程技能服务

推荐由 Agent 配置一次远程技能服务，以同一 API 令牌鉴权，通过 MCP 等方式提供实际可执行的
技能读取工具。逻辑操作为发现目录、激活技能和读取资源；这些是拟议操作，不是已存在的 API。
模型读取到目录后调用工具，服务按权限返回选中正文，结果由 Agent 带入后续模型请求。

网关只注入目录却没有可执行的读取工具，不能实现渐进式披露。
MCP 不会自动让所有 API 客户端具备工具执行能力，必须核对目标 Agent 的接入能力。
Default、Classic 操练场如果要验证该模式，也需接入相同的工具循环，不能只换一个令牌就宣称支持。

### 现有客户端零改造

如果要求任意 API 客户端只用原令牌就可工作，网关需要注册内部读取工具，截获模型调用，
读取技能、回填工具结果并再次请求上游。只拦截内部工具，保留客户端原工具调用与参数。
必须处理内部与客户端工具混合调用、流式事件、循环上限、取消、重试及每次上游用量。
同一内部工具循环固定实际分组；必须换组时，清理网关自行增加的技能正文与工具结果，
重新选组、发现和授权。不能只重做目录却把原分组授权的正文继续发往新分组。

该方案把网关扩展为部分 Agent 运行时，需分别验证 Chat、Responses、Claude 和 Gemini 的
工具调用协议与上游能力；尚未选择该方案，也不能承诺不支持工具调用的模型具有同样能力。

## 令牌与实际分组授权

- 沿用令牌归属、启停、有效期、IP 和限流校验；读取时重新检查安装启用状态、模板发布状态与版本。
- 发现与激活均受稳定 Group.Id 白名单约束，页面只展示 Group.Name。
  不能把令牌可能使用的分组并集当作本次实际分组授权。
- 独立 MCP 请求不知道网关刚才选中了哪个实际分组。不能信任客户端传入的任意分组，
  也不能用“该令牌最近一次分组”缓存：同一令牌会并发请求，auto 和重试会换组。
- 远程服务方案需要请求范围的授权能力，例如在实际路由选定后签发短时读取凭证，绑定
  令牌、调用 ID、实际分组、技能版本和有效期；工具读取同时验证调用令牌及当前权限。
  该机制是待实现的候选设计，不代表现有 MCP 协议已提供这种授权。
- 若首期只支持固定分组，必须在页面和协议中明确限制；不能悄悄降低用户已确认的实际分组规则。
- 下架、停用和卸载可以阻止后续读取，无法收回 Agent 已读入本地历史的正文。
  后续换组也不能保证从客户端历史删除已有资料，应区分本次披露与用户自行提交的内容。

## 正文可见性与审计

用户页面可以继续只提供安装、卸载和摘要。但允许令牌持有人使用的 Agent 读取正文后，
不能再承诺该持有人绝对无法获得正文；工具结果本身就是一次经过授权的明文披露。

日志记录包、技能、版本、资源路径和披露阶段，不额外记录正文、令牌或读取凭证。
远程读取不调用收费上游；正文进入后续模型请求时按实际输入计费。
网关代行工具循环时，所有内部上游轮次均须独立统计、预扣和结算，不能只记录最终回复。

## 验证计划与完成门槛

- 多技能合集首次请求只有目录；激活其中一项仅返回该项，引用资料再次按路径读取。
- 同名技能、缺失描述、相对引用、UTF-8 字节限制、越界路径、过期版本及损坏包有确定性验证。
- 他人令牌、卸载、停用、下架、失效凭证、分组名称与 code 不同、auto 和跨组重试均覆盖。
- 按最终选择验证 Agent 的真实工具执行；本地模拟不能替代目标 Agent 的兼容性验收。
- Default 与 Classic 管理界面保持同一数据与权限契约；实际页面改动分别测试及构建。
- 所有 Go 测试设置 `-timeout=60s`；涉及 relaykit 时执行独立构建。
- 存储使用三数据库兼容方案，迁移与回滚均有明确边界；通过后才更新能力总览与发布状态。

当前只完成源码和官方规范核对，以及本设计记录；没有渐进式披露功能的测试通过声明。

## 跨项目影响评估

NewAPIForDouDi：按需加载对多技能令牌有价值，但必须先核对其 Agent 工具接入、分组和计费契约，
目前只有草案，不建议直接移植。

NewAPIModifyByGang：若存在相同的技能全文装载，值得后续分享分层模型与读取权限设计；
未核实其运行时能力，同样不能当作通用补丁照搬。当前不向兄弟项目发送消息或创建 Issue。
