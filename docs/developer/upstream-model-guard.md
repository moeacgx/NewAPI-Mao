# 上游模型校验扩展

## 外置交付方式

本模块以独立 ZIP 上传到「扩展模块」安装、启用和卸载，不属于随宿主自动安装的内置模块。
源码位于 `extensions/upstream-model-guard`，不在 `extension/builtin` 的嵌入范围内。
ZIP 包包含清单、Default/Classic 原生界面和插件自己的语言资源。

当前宿主的外部扩展运行时只支持静态资源或 HTTP 代理，没有后台响应拦截执行器。
因此实时采集、持久化关渠与通知入队仍需要本项提供的宿主支持；仅上传 ZIP 到原有旧版本
不能实现实时检测。插件未安装、未启用或卸载后停止检测，已关闭渠道保持关闭。
宿主支持与可安装 ZIP 分别交付，测试必须验证未预装、真实 ZIP 上传、启停、卸载与重启后不复活。

## 目标与范围

`upstream-model-guard` 按实际使用分组、客户端请求模型与上游响应声明的模型名进行校验。
Root 配置多条规则，每条可选择多个分组、一个请求模型及多个允许的上游模型。
数据库保存分组 ID，接口以分组代码提交规则，页面与通知使用显示名称；删除后以同名重建的分组不会继承旧规则。
完整模型名区分大小写，忽略首尾空白，不进行前缀或模糊匹配。
请求模型在绑定检测时固定；供应商适配器后续为计费改写模型名，不改变规则匹配对象。

首次观察到不匹配的非空上游响应模型时，持久化关闭整条出错渠道，所有分组、模型和密钥停止参与新请求调度。
分组选择仅限制检测触发范围。禁用不修改渠道模型列表、映射或密钥内容；渠道状态置为需人工恢复的禁用状态，
普通健康检查不得自动恢复。管理员排查后在渠道管理中显式启用。
自动错误禁用、健康恢复和 TokensPro 并发同步的状态转换必须在持有渠道行锁时检查该人工禁用标记，
不得将其覆盖为可自动恢复状态；人工渠道管理入口仍可显式恢复。

尚未返回模型名的响应不触发禁用。本模块检查供应商声明的模型标识，不能证明实际模型身份。
流式响应逐次检查已经采集的非空模型字段；当前响应与已在途请求不撤回，禁用作用于后续选渠。
检测入口为正常转发链路 `controller.Relay`，覆盖宿主已实现响应模型采集的协议；
渠道管理的独立测试入口、未采集该字段的协议、Realtime 与异步任务不承诺覆盖。
若错误响应也进入模型采集点，其非空模型声明同样参与校验，不以计费或日志写入成功作为前提。

## 配置与接口

接口前缀为 `/api/extensions/upstream-model-guard`，要求 Root 权限、禁缓存与限流。

- `GET /config`：返回 `config_version`、`enabled` 和 `rules`。
- `PUT /config`：提交 `expected_version`、`enabled` 和 `rules`，版本冲突返回 409。
- `GET /groups`：返回分组 `id`、稳定 `code` 和显示 `name`。
- `GET /records?page=1&page_size=50`：分页返回触发记录及总数。

记录中的 `group` 保留内部代码，`group_name` 按 `group_id` 批量解析当前显示名称，不新增数据库列。
分组删除或名称缺失时回退记录中的原标识，同 code 重建的新分组不能冒充旧分组的名称。
Default 与 Classic 的分组选项只展示名称，不附加 code；提交值仍为 `group_codes`。
重复规则、停用分组等可解析分组身份的错误提示也使用显示名称。

每条规则为 `{"enabled":true,"group_codes":["default"],"model":"client-model","upstream_models":["provider-model"]}`。
模块默认关闭。启用的规则不得在同一分组和请求模型上重叠；空分组、空模型、未知分组及超限配置应拒绝。
最多 100 条规则，每条最多 100 个分组、50 个上游模型；模型名最多 255 字节，不接受控制字符。
配置写入记录 Root 操作审计。读取接口不要求模块开启，便于停用期间排查及配置。
暂停检测、删除规则或关闭扩展均不自动解除已经发生的禁用，须在渠道管理中显式恢复。

## 数据与安全边界

配置及禁用记录存储于主数据库，使用 GORM 通用字段和文本 JSON，兼容 SQLite、MySQL 与 PostgreSQL。
以渠道 ID 和启用状态执行条件更新；同一轮并发观察只生成一次禁用记录和通知。
记录保留触发时间、渠道名称及 ID、分组、请求模型、实际模型、允许模型和请求 ID，不保存密钥、请求正文或响应正文。
开启本模块的节点在取渠道密钥前读取数据库状态，旧缓存不能继续选中已禁用渠道，
初次分发可回退至其他候选。数据库状态读取失败时拒绝该次选渠。
扩展宿主的模块状态保存在所用模块目录的 `state.json`，各进程维护独立的状态快照。
共享模块目录不会自动刷新其他进程的快照，规则配置则保存在共享数据库；多节点部署必须在每个转发节点
安装相同宿主版本并开启或刷新模块状态。未开启模块的节点沿用原有周期性渠道缓存刷新，不保证立即阻断。
配置变更必须用版本校验，故障不得被描述成成功禁用。
每次请求绑定规则快照，禁用事务再次检查配置版本；关闭或修改配置后，旧快照不再执行禁用。
观察回调使用独立的 3 秒上下文，同步持久化渠道状态、记录及通知入队；数据库或通知入队失败
会回滚事务并记录系统错误，后续声明可重试。Telegram 网络失败不回滚已提交的禁用。
禁用记录长期保留，当前不提供自动清理或删除接口。

## 界面

使用外置原生扩展入口，提供检测总开关、规则列表编辑、分组多选、模型对应关系和禁用记录。
用户确认同时支持 Default 与 Classic；两套入口分别使用各自宿主 API，
共享业务契约且不跨模板引用组件。新增文案使用 i18n，模块遵守现有主题和响应式布局。
Default 页面为 `/extensions/upstream-model-guard/index`，Classic 为
`/console/extensions/upstream-model-guard/index`；两套通知中心地址均为 `/notification-center`。
插件自行携带独立 i18n 命名空间的七语资源，并兼容 Classic 的 `zh-CN`，不修改宿主语言包。

维护 `public/source/page.mjs` 与对应模板适配器后，执行
`node extensions/upstream-model-guard/public/source/build.mjs` 生成独立原生入口。
CSS 分别维护在 `public/native/default.css` 与 `public/native/classic.css`。
使用 `extensions/upstream-model-guard/build-package.ps1` 构建上传 ZIP 与完整性校验值，
上传包不包含源码构建脚本、测试或宿主实现。已有两套宿主 SDK 即可加载页面控件。

## 通知中心

模块声明 `extension.upstream-model-guard.channel_disabled` 事件，在通知中心的事件列表中选择后，
由任务配置现有 Telegram Bot、接收 Chat ID、提及对象和消息模板。模块不读取 Bot Token。
默认通知包含渠道名称、ID、触发分组、请求模型、允许的上游模型和实际返回模型。
事件负载 `group` 与 `comparison` 内的分组文本按稳定分组 ID 在入队事务中读取显示名称，
无名称时才回退原标识。已入队消息保留产生时的名称，后续分组改名不会改写历史通知。
渠道禁用立即持久化，通知通过通知中心队列异步发送；重复流式块及并发命中不重复通知。
通知沿用现有调度周期和失败重试策略，不保证 Telegram 在响应帧处理时已收到消息。
没有启用的通知任务时，渠道仍然关闭并保留触发记录，不发送 Telegram 消息。
